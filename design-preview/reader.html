工具：模型的执行权代理

模型本身只会生成文本——它不能读文件、不能发请求、不能改代码。 让它「做到」这些事的，是 Harness 替它代持的执行权： 你把每个能力包装成一个工具，模型在需要时说出工具名和参数， Harness 负责真正执行，再把结果回填给它。

一次典型的回合是这样走的：模型输出 {"tool":"read_file","path":"main.py"}， Harness 读到文件内容，以 tool_result 的身份塞回对话， 模型看到内容后继续推理——要么再调一个工具，要么给出最终回答。 这个「说→执行→回填→再说」的循环，就是 agent 与普通对话的全部区别源[1]。

⚠ 坑是主菜 · 工具给多了，模型反而变笨

新手最容易犯的错，是把所有能力一股脑塞进工具清单——「反正多多益善」。 实际后果是模型要在几十个工具里反复犹豫，选错的概率随清单长度上升， token 花在选择上而不是干事上。

怎么避免：每个 agent 只装配它职责内的工具。 答疑 agent 永远不需要 write_file—— 给它就是埋一颗误操作的地雷。

所以工具设计的第一性原理不是「能力齐全」，而是动作空间刚好： 少一个干不了活，多一个就多一分选错的风险。下一节我们把这套思路 放进循环里，看步进和终止条件怎么定源[2]。

工具和 function calling 到底是什么关系？
一回事的两个名字：function calling 是各家 API 里「模型说要调哪个函数」的机制名，工具是 Harness 视角下 「被调的那个能力」的产物名。你在课件第 2 节 见过的消息回填，就是两者咬合的齿轮。
