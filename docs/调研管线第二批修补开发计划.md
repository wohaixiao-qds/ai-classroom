# 调研管线第二批修补开发计划（持久检查点 + 状态语义 + 历史压缩）

> 状态：待执行 · 创建：2026-11-25 · 来源：E2E 闸门测试（10+ 次派单，缺陷 #1-#9）+ 修订意见两轮审查
> 前置：第一批边界控制已落地验收（84501a7 + 45a00db，223 测试基线）
> 执行方式：Agent Team 多窗口并行，按阶段分派，每阶段独立提交独立验收

---

## 背景与目标

第十次派单起管线在真实环境（中转抖动/引擎欠费/模型不收敛）暴露 9 个缺陷，第一批边界控制
（max_retries=0/差异化超时/引擎熔断/query cache/传输重试收口）已落地并验证「7 分钟快速明确失败」。
但仍有结构性缺口：

1. **材料全丢**：传输连击终止/覆盖闸最终失败时，已抓 30 页正文没有任何可恢复产物（`_loop`
   只在覆盖闸通过后才 `_save` 正式路径；异常处理里保存防不了 kill -9）
2. **上下文膨胀**：调研消息历史全量保留（网页正文进 tool_result），单轮输入 89k 且持续增长，
   疑似导致模型收笔意愿下降（待验证假设，需指标验证）
3. **状态语义混用**：draft（只有网页）/pending_review（结构过审待语义审查）/正式材料三种状态
   在文件层面无区分，备课门禁依赖运行时判断而非持久状态

**目标**（验收标准，来自修订意见）：
- 中断后能恢复（kill -9 级）
- 已抓正文不重复请求（跨恢复周期）
- 压缩后引文仍可定位（逐字命中快照）
- 审查失败仍阻止备课（门禁不绕行）

## 阶段一：持久检查点 + 状态语义三分（T2.1~T2.4）

### T2.1 抓取级持久检查点 【P0】
**现状**：`successful_fetches` 只存进程内存；异常路径的保存只在 validator 失败分支。
**改动**（`app/agent/research.py`）：
- `_loop` 每次成功 `fetch_page` 后增量写检查点文件
  `data/research/{slug}.material.checkpoint.json`
- 内容：`{url: {title, body(截断8k原文), sha256, fetched_at, call_index}}` + 当前候选材料（若有）
  + 未解决缺口清单 + `research_context_hash` + 阶段标记（initial/gap1/gap2）+ 执行版本
- 写入方式：临时文件 + `replace` 原子替换（现有 checkpoint 惯用法）
- **独立于现有 publication checkpoint**（那是审查结论缓存，勿混淆——命名用
  `material.checkpoint.json` 区分）
**验收**：kill -9 后检查点文件存在且完整；重跑同一课不重复抓取已存正文

### T2.2 状态语义三分与文件后缀 【P0】
**现状**：draft/pending_review/正式三种状态在文件层面无区分。
**改动**（research.py + cached_material 消费方）：
- 文件后缀约定：
  - `{slug}.material.checkpoint.json` —— T2.1 检查点（可恢复现场）
  - `{slug}.material.draft.json` —— 有网页+候选材料，未过覆盖闸
  - `{slug}.material.pending_review.json` —— 结构+引文定位已过，等语义审查
  - `{slug}.material.json` —— 正式（全闸通过）
- `cached_material()` 只认正式后缀；draft/pending 不得被备课消费
- 恢复策略按状态区分：checkpoint → 跳过已抓正文续调研；draft → 只跑覆盖闸补挖；
  pending_review → 只跑证据语义补审（复用现有 `_report_review` 断点续接）
**验收**：四种状态文件互不误认；draft 不可被 `run_prep` 消费；pending 补审不重新联网

### T2.3 失败路径落 draft + 快速失败保存 【P0】
**现状**：传输连击终止（第一批新增）直接 raise，30 页正文全丢。
**改动**：
- `_loop` 轮次耗尽/传输连击的 raise 前，将已抓正文+候选材料写 draft 文件
- `research_material` 的 except 分支捕获后返回结构化结果
  `{"ok": False, "draft_path": ..., "gaps": [...], "fetched_count": N}` 供上层展示
- job_runner 侧 FAILED 消息带 draft 路径与缺口摘要
**验收**：传输连击终止后 draft 文件可被下一次点单续用（T2.2 的恢复策略）

### T2.4 阶段计时埋点 【P1】
**改动**：`update_run` 增加分阶段耗时（抓取累计/模型思考累计/审查累计）——现 `research_cost`
已有 generation_s/tool_s/review_s 三项，补「阶段」维度（initial/gap 轮次各自耗时）
**验收**：trace 中可读出每阶段耗时，作为后续优化基线

## 阶段二：历史压缩 + 按需回读（T2.5~T2.7）

### T2.5 历史压缩触发与保留清单 【P0】
**现状**：`messages` 全量保留；单轮输入 89k 且随轮次线性增长。
**改动**（research.py `_loop`）：
- **触发**：输入体积优先（估算 >40k token 时压缩），轮数 ≥4 为辅助条件
- **压缩产物**（替换 messages[1:-1]，保留首尾）：
  - 课程 goal/scope/排除项原文（不压缩）
  - 最新门禁反馈原文（不压缩）
  - 最近 1 轮完整交互（不压缩）
  - 更早历史 → 结构化摘要：候选要点（text+逐字 quote+source_id+快照哈希+quote_start/end）
  - **「引文已命中快照」与「语义审查 supported」分开标记**，不合并为「已确认」
- 目标：单轮输入 20-40k；**验证指标**：覆盖缺口率不升、引文定位成功率不降、交付重试次数不增
**验收**：压缩后重跑同课，三项指标与不压缩基线对比无退化

### T2.6 本地快照回读工具 【P0】
**改动**（tools.py + RESEARCH_TOOLS 清单）：
- 新工具 `read_snapshot(url, offset=0, length=4000)`：从 T2.1 检查点的已存正文读指定段落
  （**不重新联网**——AnySearch 提取已截断 8000 字符，回读上限即已保存正文）
- 返回带定位标记（offset 标头），模型引用后仍走既有引文校验链
- 给调研 agent 的工具说明明确「正文已退出版本历史，需要看原文段落时用此工具」
**验收**：压缩后的循环里模型能用 read_snapshot 拿到引文上下文；引文校验通过率不降

### T2.7 指标验证跑 【P0】
**改动**：无代码——用中转恢复后的真实派单跑 T2.5 验证指标
**验收**：交付成功率/引文定位成功率/缺口率三项达标；不达标则调压缩策略（保留更多轮次）

## 阶段三：增量复用 + 并发搜索 + 可视化（T2.8~T2.10，依赖阶段一二）

### T2.8 增量材料复用 【P1】
**前置**：先打通「旧材料+旧快照+新材料」合并验证（当前补挖循环**没有继承旧材料**——
gap_prompt 只有文字声明，`_loop` 重建全新抓取状态，已核实）
**改动**：
- 补挖循环入参带旧材料+旧快照，`successful_fetches` 从检查点预填（已抓 URL 不重复抓）
- context diff：goal/scope/prereqs 逐字段比对；`prereqs` 变化按「讲解深度变化」处理
  （不按字符串 diff 判断内容适用性）
- 合并后对新完整约束**全量重跑覆盖检查**（不能只查缺口清单）
**验收**：改 scope 后重派，未变方面的材料点被复用（来源溯源保留），只抓新增方面

### T2.9 搜索并发 【P1】
**前置**：T2.4 的 provider 计时数据已产出（⏱ 分项日志已上线）
**改动**（tools.py `web_search_multi`）：
- ThreadPoolExecutor 并发可用引擎；**统一 deadline**（排队+请求+重试都在内，不能用裸
  `future.result(timeout)`——with 退出仍会等线程）
- 进程级并发上限（AnySearch 匿名接口并发容忍度未测，先并发度 2 小样本）
- 先小样本对照（P95/超时率/限流率），数据支持后再全量
**验收**：单次 multi 搜索 P95 < 4s；AnySearch 无限流 429

### T2.10 预算可视化 【P2】
**改动**（JobFeed.tsx + jobs 日志）：
- 只显示**实际次数**（初始/补挖分开：「补挖 1/2 · 第 2/6 轮」）；预算分母先落实限制再显示
- 耗时用服务端记录（`update_run` 时间戳），**不用前端挂载计时**（刷新即重置的坑已知）
**验收**：刷新后显示的耗时与任务实际耗时一致

## 已知风险与取舍（已拍板）

- 历史压缩后模型看不到已滚出上下文的网页全文——按需回读本地快照补偿；回读上限=
  已保存的截断正文（AnySearch 8k），不重新联网
- 「只剩摘要不影响质量」不预设结论——用三项指标验证
- draft 保存的正文是 AnySearch 截断版（8k），非完整 HTML
- 进程内熔断/缓存作用域=单任务（后台 job 独立子进程），跨任务共享状态后置
